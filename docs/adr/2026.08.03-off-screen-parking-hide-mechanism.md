# Off-screen parking as the hide mechanism for workspaces and stacks

## Context

Two core features need to make windows disappear without closing them:
switching a workspace (hide the old set, show the new)
and selecting a tab in a stack (show one window, hide the siblings
sharing its rectangle). On pure Accessibility, with SIP enabled, vase cannot reorder windows in the WindowServer,
so it needs a way to "hide" a live window that it *can* drive through the Accessibility API.

The reference projects split on this: yabai reorders windows directly (SIP off, instant, flicker-free), while AeroSpace,
staying on pure Accessibility, moves hidden windows off-screen. Vase has committed to pure Accessibility,
so it must pick an AX-drivable mechanism. A future reader would wonder why hidden windows aren't simply minimized
or hidden via the OS, hence this record.

## Options

1. **Off-screen parking.** Move hidden windows to coordinates far outside any screen (e.g. x = -30000);
   unpark into the target rectangle when shown. Same primitive for workspace switches and non-selected stack tabs.
   Cost: moving a window via AX is a per-app round-trip that can lag or flicker for slow apps,
   and a few apps resist being moved or snap back.
2. **AX-minimize.** Genie-animate to the Dock. Visually loud and slow, poor for fast tab-switching.
3. **App-hide (Cmd-H).** Hides *all* of an app's windows at once, too coarse for per-window stacks.
4. **Native macOS Spaces.** Not reliably scriptable without private APIs;
   incompatible with the pure-Accessibility commitment.
5. **SIP-off window reordering (yabai-style).** Instant and clean,
   but rejected with the pure-Accessibility / no-SIP decision (see the deliberate-placement ADR).

## Recommendation

Option 1. It is the only mechanism that is AX-drivable, per-window, and fast enough for interactive switching,
and it unifies workspace switching and stack tab selection under one primitive.

Switch latency remains the single biggest risk to the crown-jewel stack feature.
A standalone `osascript` spike to measure it was attempted and dropped:
driving AX through System Events required activating apps, which steals keyboard focus from the controlling terminal
and cannot be safely bounded. Rather than build a bespoke harness, we rely on prior art
(**AeroSpace already ships this exact off-screen-parking mechanism on pure Accessibility to real users**)
and defer latency validation to the real macOS backend, where vase fully controls the event loop and focus.

## Decision

Adopt **off-screen parking** as the hide mechanism for both workspace switches and non-selected stack tabs.
Latency is validated during the macOS backend implementation (not a separate spike),
leaning on AeroSpace's proven use of the same approach.
Rejects AX-minimize, app-hide, native Spaces, and SIP-off reordering.

**Validated (2026-08-04):** the `vase-macos` latency harness parked+restored
a full-screen Google Chrome window (1920×998) 20 times:
round-trip min 16 ms, median 21 ms, max 161 ms (a first-iteration warm-up outlier). Per-move ≈ 10 ms,
well under the ~40 ms "feels like a tab" threshold. Decision confirmed.

**Refinement (2026-08-06):** off-screen parking is the hide mechanism for **workspace switches only**, not stack tabs.
A stack's members are co-located at the same rectangle,
so a hidden tab is **occluded by raising the selected one (z-order)**. No movement at all.
Switching a stack tab is therefore a pure raise (the reducer emits only `FocusWindow`, no `Render`): instant,
and it fixes the visible "sliding off to the left" the parking-per-flip approach caused. Parking remains necessary
only for a set of windows at differing positions that one raised window can't occlude,
i.e. the windows of an *inactive workspace*.
