# Windows chrome on Direct2D, not WinUI 3

## Context

The Windows backend should look native, the way the AppKit chrome does (should) on macOS. WinUI 3 is the
obvious candidate.

But vase's chrome is not an app window. It is a set of surfaces drawn _on top of other apps'_
windows: always-on-top, never activating, click-through and present on every workspace.
On macOS that is a borderless `NSPanel`.

That set of requirements is the one thing WinUI 3 is worst at:
Note that the _native look_ and the _framework_ are separable. Mica, the
system accent colour, the light/dark preference, Segoe UI Variable, and WinUI's corner radii are all
reachable from a plain HWND.

## Options

1. **WinUI 3 / XAML islands.** Highest fidelity. Has every problem above, and most of the project's risk would sit in the binding and
   bootstrapping layer rather than in vase.
2. **Direct2D + DirectWrite on a layered, non-activating HWND**, with the native look taken from OS
   tokens: `DwmSetWindowAttribute` for the Mica backdrop and rounded corners, `UISettings` for the
   accent colour and light/dark. All in the `windows` crate, no extra runtime, no packaging, and it
   cross-compiles.
3. **GDI+ / plain GDI.** Simplest, but no per-pixel alpha and no decent text rendering; the bar's
   rounded powerline shapes would alias badly.

## Recommendation

Option 2. It is the only option that satisfies the overlay's actual requirements. The Fluent _look_ comes from the same OS tokens WinUI 3 itself reads,
and vase draws its own shapes anyway.

WinUI 3 stays a reasonable choice if vase ever grows a real settings window, which _is_ an ordinary
activating app window. It has none today.

## Decision

Adopt **Direct2D + DirectWrite + DirectComposition on a layered `WS_EX_NOACTIVATE | WS_EX_TRANSPARENT | WS_EX_TOOLWINDOW` HWND**,
with the palette derived from `UISettings` (accent, light/dark) and the backdrop from `DwmSetWindowAttribute(DWMWA_SYSTEMBACKDROP_TYPE)`.

This rejects WinUI 3 for the chrome specifically, not for vase forever.
Revisit it only for a window that genuinely wants to activate.

The whole API surface this needs was verified to compile for `x86_64-pc-windows-gnu` before the
decision was taken.
