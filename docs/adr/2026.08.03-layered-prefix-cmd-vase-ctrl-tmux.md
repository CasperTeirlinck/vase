# Layered prefix: Cmd = vase, Ctrl = tmux, Cmd-a chord as the vase prefix

## Context

Vase captures keys via a global event tap, *above* the user's existing
two-layer tmux prefix scheme (`Ctrl-a` outer, `Ctrl-e` inner) and a intricate,
device-specific Karabiner + Ghostty remap chain. The chain is compensating:
Karabiner swaps Left-Command↔Left-Control on external keyboards and
Command↔fn on the built-in keyboard; Ghostty then maps `cmd+a → \x01` so the
user's natural prefix finger reaches tmux as `Ctrl-a`. vase's tap observes
keys *after* Karabiner.

The risk: if vase claimed the same chord the user uses for tmux, it would eat
the tmux prefix before the terminal saw it — or, if it forwarded that chord when
the terminal is focused, vase commands (e.g. focus the browser to the right)
would be unreachable from the terminal. The user explicitly requires vase to
remain available even while the terminal is focused, and requires the existing
tmux/Karabiner/Ghostty chain to stay untouched.

A future reader would wonder why vase doesn't simply reuse `C-a`, and why the
prefix is a modal tap on a remapped key — hence this record.

## Options

1. **Shared `C-a` with context-aware forwarding.** vase taps the chord and
   passes it to tmux when the terminal is focused. "Same key everywhere," but
   needs fragile tmux↔vase coordination and blocks vase commands in the
   terminal — the rejected requirement.
2. **Distinct outermost prefix, tmux-mirrored grammar.** vase owns a
   collision-free prefix; once armed, sub-keys mirror the user's tmux bindings.
   Always available; never touches the tmux chain.
3. **Right-hand modifier prefix.** A pristine (Karabiner-untouched) right
   modifier as the prefix. Robust, but not the key the user wants.

## Recommendation

Option 2, realized as: **`Cmd = vase` (the user's currently-free physical
Command key, which Karabiner maps to `fn` and is unused as a prefix), `Ctrl =
tmux` (the physical fn key, untouched).** The prefix is the **`Cmd-a` chord**,
mirroring tmux's `Ctrl-a`: press `Cmd-a`, release, then a command key. vase
owns its own keybindings (a modal prefix needs in-process state) rather than
relying on an external hotkey daemon.

## Decision

Prefix layers are distinguished **by modifier** — Cmd for the OS/window layer
(vase), Ctrl for the terminal layer (tmux) — bound to two physically
distinct keys, so both are single-tap and always available with zero
interception conflict. The precise signal-routing for the physical Command key
(one Karabiner line vs a vase-owned event tap claiming the `fn`-flagged
chord) is an implementation detail deferred to build time; it may differ per
keyboard. `Cmd-a`-as-Select-All is recovered via a tmux-style `send-prefix`
binding. Rejects option 1 (shared prefix / context-forwarding) and any change to
the existing tmux, Karabiner, or Ghostty configuration.

## Correction (2026-08-05)

This ADR originally described the prefix as a "modal tap" of the Command key
*alone*. That was a misinterpretation: the user's intended prefix is the
**`Cmd-a` chord** — press Command+`a` together, exactly like their tmux
`Ctrl-a` — then release and press a command key. The event-tap implementation
initially built a bare-modifier-tap detector; the `input-probe` run surfaced the
mismatch and it was reworked so the prefix is a chord binding that arms the
router. A bonus: tapping only `KeyDown` (never `FlagsChanged`) means the Command
press/release still reach apps, so consuming the `Cmd-a` keydown leaves no
"stuck modifier" downstream. The signal-routing note above still holds; the
`Cmd-a` chord is what routing must deliver.
